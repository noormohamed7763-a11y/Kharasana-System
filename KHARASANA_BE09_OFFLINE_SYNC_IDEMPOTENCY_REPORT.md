# KHARASANA BE-09 — OFFLINE SYNC, IDEMPOTENCY & DATA RELIABILITY REPORT

## A. Executive Summary

This report documents the implementation of **Idempotency Infrastructure** and **Offline Sync Support** for the Kharasana Backend (BE-09). The primary goal was to ensure that sensitive operations (Create Order, Create Phone Order, Add Payment) cannot be duplicated when Flutter re-sends requests due to network issues or app restart.

### Key Achievements:
- ✅ **Idempotency Records Entity** with Unique Index on `(UserId, Key)`
- ✅ **IdempotencyService** with `CheckAndInitializeAsync` + `CompleteAsync` + `FailAsync`
- ✅ **OrderCommandService** integration for 3 sensitive operations:
  - `CreateOrder` — prevents duplicate order creation
  - `CreatePhoneOrder` — prevents duplicate phone order creation (including new client onboarding)
  - `AddPayment` — prevents duplicate payment recording
- ✅ **Database Migration** `20261104225600_AddIdempotencyTable` applied
- ✅ **API Contracts** updated in Controllers to accept `Idempotency-Key` header
- ✅ **Unit Tests** extended to verify idempotency behavior
- ✅ **Flutter Sync Architecture** identified and documented (PendingActionsDataSource, SyncService, OrderCreationController)

### Single Source of Truth:
The **Backend remains the authoritative source** for all commercial data. Flutter local storage (Hive) is used only as a **temporary cache** for offline operations. The `IdempotencyRecord` table in SQL Server guarantees that even if the app is reinstalled or crashes, duplicate operations are detected and prevented upon reconnection.

## C. Idempotency Design

### Idempotency Key Strategy

| Property | Value/Strategy |
|----------|---------------|
| **Header Name** | `Idempotency-Key` (sent from Flutter, received in Backend) |
| **Key Generation** | UUID v4 generated by Flutter **before** sending request |
| **Key Persistence** | Stored locally in Hive (same box as pending action) to survive app restart |
| **Key Uniqueness** | Must be **globally unique per user per operation type** — Flutter must not reuse keys |
| **Key Lifetime** | No explicit expiry in current implementation — persists until manually cleared |

### Request Hash Computation (Backend)

The `RequestHash` is computed as:

```csharp
sha256(userId + ":" + operationType + ":" + json(requestDto))
```

This ensures:
- Same key + same data → `IsDuplicate=true` → return stored result
- Same key + different data → `ConflictException` (409) → reject request
- Different key → process as new request

### Operation Handling Rules

| Scenario | Backend Action |
|----------|---------------|
| **First request with new key** | Creates `IdempotencyRecord` with `StatusCode=0` (Processing), executes business logic, saves result via `CompleteAsync` |
| **Same key, identical data** | Returns `(IsDuplicate=true, storedResult, storedStatusCode)` — no re-execution |
| **Same key, different data** | Throws `ConflictException` with message: "Key 'X' used with different data for operation 'Y'" |
| **Failed previous attempt** | `StatusCode=0` or `StatusCode >= 400` → allows retry (new `CompleteAsync` call overwrites) |
| **Successful previous attempt** | `StatusCode 2xx` → returns stored result immediately, skips business logic |

### Protected Operations (Currently Enabled)

| Operation | API Endpoint | Header Required |
|-----------|-------------|----------------|
| **Create Order** | `POST /api/Orders` | `Idempotency-Key` |
| **Create Phone Order** | `POST /api/Orders/phone-order` | `Idempotency-Key` |
| **Add Payment** | `POST /api/Orders/{id}/payments` | `Idempotency-Key` |

## F. Protected Operations

The following operations now have **Idempotency Protection** guaranteed by Backend:

| Operation | Endpoint | Protection Mechanism |
|-----------|----------|---------------------|
| **Create Order** | `POST /api/Orders` | `Idempotency-Key` checked before creation. If key exists with same hash → returns stored OrderDetailsDto. If different hash → 409 Conflict. |
| **Create Phone Order** | `POST /api/Orders/phone-order` | Same as above. Additionally stores `NewClientTemporaryPassword` in result payload for first-time clients. |
| **Add Payment** | `POST /api/Orders/{id}/payments` | If duplicate key detected → returns silently (no new payment created). If key exists with different data → 409 Conflict. |

**Failure Behavior:**
- If operation fails after key creation but before result storage → key record remains with `StatusCode=0` (allowing retry)
- If operation succeeds → `CompleteAsync` stores result permanently
- If user retries with same key after success → receives stored result immediately, no duplicate created

## G. API Contract

### Header: `Idempotency-Key`

| Field | Description |
|-------|-------------|
| **Name** | `Idempotency-Key` |
| **Type** | String (UUID v4) |
| **Required For** | `Create Order`, `Create Phone Order`, `Add Payment` |
| **Location** | HTTP Request Header |
| **Client Responsibility** | Generate once per operation, store locally, send with every retry |

### Success Response (Duplicate Request)

When a duplicate request is received (same key, same data):

```json
{
  "success": true,
  "message": "Order created successfully",
  "data": {
    "orderId": 123,
    "orderNumber": "ORD-20261105-abc12345",
    "status": "Pending",
    "totalPrice": 1500.0,
    "...": "other order details"
  }
}
```

**Note:** The exact shape depends on the operation, but the key point is: **no new database record is created**, and the **same response is returned**.

### Error Response (Duplicate Key with Different Data)

```json
{
  "type": "ConflictException",
  "title": "409 Conflict",
  "detail": "مفتاح Idempotency 'uuid-12345' مستخدم مع بيانات مختلفة للعملية 'CreateOrder'.",
  "status": 409
}
```

### HTTP Status Codes

| Situation | Status Code |
|-----------|-------------|
| First request, success | 201 (Create) or 200 |
| Duplicate request, same data | 200 (return stored result) |
| Duplicate request, different data | 409 Conflict |
| Validation failure | 400 |
| Unauthorized | 401 |
| Forbidden | 403 |
| Not found | 404 |

## H. Flutter Sync Architecture

### Current Flow (Identified)

```
1. User initiates Order Creation
2. OrderCreationController checks connectivity:
   - ✅ Online → Calls _repository.createOrder(dto) directly
   - ❌ Offline → Saves PendingAction to Hive (PendingActionsDataSource)
3. State set to SubmissionQueued, user sees "Saving locally" indicator
4. App can be closed/restarted — pending action persists in Hive
5. On app resume or manual refresh:
   - SyncService.checkConnectivity() → if online, calls sync()
6. SyncService.getPendingActions() → retrieves all pending actions
7. For each action:
   - If create_order → calls _repository.createOrder(dto) with Idempotency-Key
   - On success → _pendingActions.removePendingAction(action.id)
   - On failure → action remains pending for next retry
```

|-------------|----------|---------|

| **Store resultEntityId after sync** | `SyncService` + `PendingActionsDataSource` | After successful sync, store returned `orderId` in the pending action DTO for future reference |

## I. Retry Strategy

### Retryable Errors (Will be Retried Automatically)

| Error Type | HTTP Status | Reason |
|------------|-------------|--------|
| **Network Timeout** | N/A (no response) | Connection lost, may succeed on retry |
| **Connection Failure** | N/A | Transient network issue |
| **Temporary Server Error** | 500, 502, 503 | Server overload, usually recovers |
| **Service Unavailable** | 503 | Retry-After header may be present |

**Flutter Behavior:**
- `SyncService` checks `ConnectivityResult.none` — if no connection, defers sync
- On connectivity restore, `sync()` is called automatically or manually
- If Dio throws `TimeoutFailure` or `ServerFailure` → action **remains pending** for next sync cycle
- **Exponential Backoff** not yet implemented — pending action stays until manually cleared or next app launch

### Non-Retryable Errors (Will NOT be retried, user must intervene)

| Error Type | HTTP Status | Reason |
|------------|-------------|--------|
| **Validation Failure** | 400 | Invalid data — user must fix and resubmit |
| **Unauthorized** | 401 | Token expired/invalid — re-login required |
| **Forbidden** | 403 | User lacks permission — permission change needed |
| **Not Found** | 404 | Referenced entity deleted — user must re-select |
| **Conflict** | 409 | Data conflict (different payload with same key) — user must take action |

**Flutter Behavior:**
- `mapDioError` in `DioClient` maps these to specific `Failure` types
- `OrderCreationController.submit()` returns `SubmissionFailed` message
- Action **remains pending** in Hive, but user sees error message
- User must manually fix and re-attempt (or clear pending action)

### Current Limitations

| Limitation | Impact | planned Fix |
|------------|--------|-------------|
| **No exponential backoff** | May retry immediately if app stays online | Add `Timer` + retry count in `PendingActionDto` |
| **No max retry count** | Could retry indefinitely | Add `retryCount` field, stop after N attempts |
| **Validation errors not filtered** | User may retry invalid data | `SyncService` should check error type before re-attempting |
| **Token expiry during retry** | 401 may occur on retry | `DioClient` already has auto-refresh logic, needs extension for pending actions |

## J. Conflict Resolution

### Current Policy (Backend-Driven)

| Conflict Scenario | Backend Resolution |
|-------------------|-------------------|
| **Same Key, Same Data** | ✅ Return stored result, skip execution |
| **Same Key, Different Data** | ❌ Throw `ConflictException` (409) — user must use new key |
| **Different Keys, Same Data** | ✅ Process as two independent operations (last write wins at DB level) |
| **Previous Failed, Retry** | ✅ Allow retry — `CompleteAsync` overwrites previous result |
| **Previous Success, Retry** | ✅ Return stored result immediately — no re-execution |

### Flutter Side Conflict Handling

| Scenario | User Action |
|----------|-------------|
| **User sees "Operation already completed" message** | No action needed — operation was successful previously |
| **User sees 409 Conflict error** | Generate new Idempotency-Key and resubmit with corrected data |
| **User app restart, pending action remains** | Sync will re-attempt — if key still valid, will return stored result |

### Concurrency Control

- **RowVersion/Concurrency Tokens**: Not yet implemented for idempotency operations — relies on unique `(UserId, Key)` index in database
- **Database-Level Protection**: The `Unique Index` on `(UserId, Key)` prevents race conditions at SQL Server level — if two requests with same key arrive simultaneously, only one will succeed, the other will get a constraint violation handled by EF Core

### New Migration: `20261104225600_AddIdempotencyTable`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `Id` | `int` | Primary Key, Identity | Unique record identifier |
| `Key` | `nvarchar(128)` | `NOT NULL`, `MAX 128 chars` | Idempotency key sent from client |

| `ResultEntityId` | `nvarchar(MAX)` | `NULLABLE` | Stores OrderId, PaymentId, etc. on success |
| `ResultPayload` | `nvarchar(MAX)` | `NULLABLE` | Serialized result DTO on success |
| `StatusCode` | `int` | `NOT NULL`, `DEFAULT 0` | HTTP status code: 0=processing, 2xx=success, 4xx/5xx=failure |
| `CreatedAt` | `datetime2` | `NOT NULL`, `DEFAULT getutcdate()` | When record was first created |
| `ExpiresAt` | `datetime2` | `NULLABLE` | Optional expiry for cleanup |

### Indexes

| Index | Columns | Type |
|-------|---------|------|
| **Primary Key** | `Id` | Clustered Index (implicit) |
| **Unique Index** | `(UserId, Key)` | Non-clustered, **Unique** — prevents same key reuse per user |

### SQL Schema (Generated)

```sql
CREATE TABLE [IdempotencyRecords] (
    [Id] int IDENTITY(1,1) NOT NULL,
    [Key] nvarchar(128) NOT NULL,
    [UserId] int NOT NULL,
    [OperationType] nvarchar(64) NOT NULL,
    [RequestHash] nvarchar(64) NOT NULL,
    [ResultEntityId] nvarchar(max) NULL,
    [ResultPayload] nvarchar(max) NULL,
    [StatusCode] int NOT NULL DEFAULT 0,
    [CreatedAt] datetime2 NOT NULL DEFAULT GETUTCDATE(),
    [ExpiresAt] datetime2 NULL,
    CONSTRAINT [PK_IdempotencyRecords] PRIMARY KEY ([Id]),
    CONSTRAINT [UIQ_Idempotency_UserKey] UNIQUE NONCLUSTERED ([UserId], [Key]),
    CONSTRAINT [FK_IdempotencyRecords_Users_UserId] FOREIGN KEY ([UserId]) REFERENCES [Users]([UserId]) ON DELETE RESTRICT
);
```

### Migration Impact

- **New Table**: `IdempotencyRecords` created
- **No Data Loss**: Existing data unaffected
- **Backward Compatible**: Old requests without `Idempotency-Key` still work (key simply `null`, processed as new request)
- **Index Creation**: Unique index added — may take brief time on large tables, but expected for new table
